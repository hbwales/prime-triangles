Performance

02

Shrink the sieve before marking

For N rows, the largest integer is \(N^2\). Every composite in that range has a prime factor at most N, so a small CPU sieve supplies all the primes needed by the GPU. For each prime p, marking starts at \(p^2\): smaller multiples already have a smaller prime factor, and p itself must survive.

Store eight candidates per thirty integers

Multiples of 2, 3 and 5 can be omitted. Every other prime has one of eight residues modulo 30:

\[\mathcal R=\{1,7,11,13,17,19,23,29\},\qquad x=30q+r\longleftrightarrow\text{bit for }r\text{ in byte }q.\]

One byte therefore covers 30 integers. A set bit means “still a candidate”; marking a composite only clears its bit. This compression reduces both memory use and the amount of data the GPU must scan.

The modulo-30 byte

Green candidates remain set; crossed-out candidates have been eliminated. Plain numbers have no stored bit. The full-sieve view calculates the primes in this small example.

Remove small-prime multiples with a repeating pattern

Multiples of 7, 11, 13 and 17 repeat every \(7\cdot11\cdot13\cdot17=17{,}017\) wheel bytes. A precomputed pattern removes them when each tile is initialized, replacing four sets of strike loops with regular memory copies. The prime list and pattern are copied to the GPU once.

The small primes themselves are handled separately: 2, 3 and 5 have no wheel bits, while 7, 11, 13 and 17 are restored in the first tile. The bit representing 1 is cleared.

03

Work in batches and shared-memory tiles

The entire range need not fit in GPU memory. Process it in batches of 256 MiB of wheel bits, each representing about 8.05 billion integers. Within a batch, many CUDA blocks work independently on 96 KiB tiles.

A CUDA block is a cooperating group of threads. Each block keeps its tile in fast shared memory, close to those threads, rather than repeatedly updating the large off-chip sieve. Only the finished tile is written to global memory.

Find starting positions once, then use additions

A prime becomes active when its square reaches the current batch. Its first required multiple is at least both the batch’s beginning and \(p^2\). Prepare a starting position and the eight residue-to-bit mappings once per active prime, then reuse them across tiles.

Writing a wheel-eligible multiplier as \(k=30t+r\) gives

\[\left\lfloor\frac{pk}{30}\right\rfloor=pt+\left\lfloor\frac{pr}{30}\right\rfloor.\]

For a fixed residue r, the next multiplier turn adds 30 to k, so the next strike advances exactly p bytes and clears the same bit position. The inner marking loop can therefore use additions instead of dividing every product. Absolute positions use 64-bit arithmetic; bounded offsets within a batch or tile usually need only 32 bits.

Replace repeated division with exact integer multiplication

For a w-bit numerator v, precompute \(u=\lfloor2^w/p\rfloor\). The upper half of the product gives a quotient estimate at most one too small:

\[q_0=\left\lfloor\frac{vu}{2^w}\right\rfloor,\qquad\left\lfloor\frac vp\right\rfloor=q_0+\mathbf1_{\{v-q_0p\ge p\}}.\]

A multiply, remainder check and possible correction replace an expensive integer division while keeping the result exact.

Clear bits without losing another thread’s work

Different primes can touch different bits in the same memory word. Ordinary read–modify–write operations could overwrite another thread’s clear. Atomic AND combines the updates safely: a bit that has been cleared stays cleared, even if several threads mark it.

05

Keep large-prime marking moving forward

Large primes have few strikes in each small tile. Repeatedly scanning their records for every tile would spend too much work finding almost no hits. For large runs, primes above two million instead use a second pass over 16 MiB windows in global memory.

One thread follows one prime’s multiples in increasing order, clearing their wheel bits. The larger window amortizes the prime-record lookup across much more of the sieve and keeps repeated accesses localized for the GPU cache.

Carry just enough state to resume

At the window boundary, save the next byte offset relative to the following window and the position in the eight-residue cycle. These fit in one 32-bit word per prime. The next pass resumes from that state, avoiding repeated large-coordinate division and first-strike searches. Newly active primes still enforce the \(p^2\) starting boundary.

Each prime’s thread owns its saved state, so updating it needs no atomic operation. Clearing shared sieve words still needs atomic AND because different primes can hit the same word.

Avoid clears already done by the small-prime pattern

Before issuing a global atomic, test whether the target is divisible by 7, 11, 13 or 17. Those candidates are already clear. Rejecting them removes approximately

\[1-\frac67\frac{10}{11}\frac{12}{13}\frac{16}{17}\approx32.3\%\]

of the candidate global atomic updates. The thread still advances through those wheel hits, but avoids their memory operation. The small-prime pattern’s period allows these divisibility tests to use bounded 32-bit positions.

The shared-tile pass finishes before the large-prime pass, and both finish before counting. This ordering prevents a later tile store from restoring a bit already cleared by a large prime.

06

Count prime bits in parallel

After marking, every surviving wheel bit represents a prime. Count whole words with the GPU’s population-count instruction, which returns the number of set bits. One 32-bit word covers 120 integers, so most counting work is a word load and a bit count rather than a test of each integer.

Mask just the interval boundaries

For row n, the first integer, centre and last integer are

\[a_n=(n-1)^2+1,\qquad m_n=n^2-n+1,\qquad b_n=n^2.\]

Count \([a_n,m_n-1]\) and \([m_n+1,b_n]\); test the centre bit separately. Each interval is clipped to the current batch. Precomputed residue masks discard unwanted bits in the first and last words. All interior words can be counted directly; if both endpoints share a word, apply both masks to it.

Reduce 256 thread totals to one row count

One block of 256 threads handles one row’s overlap with a batch. Neighboring threads read neighboring words, then advance by 256 words. Each thread keeps separate left and right totals in registers.

256 thread totalsEach thread counts its assigned words.
8 warp totalsEach 32-thread warp adds its register counts.
64 shared bytesOne thread per warp stores a pair of subtotals; the block synchronizes.
One final warpCombine the eight pairs into the row’s left and right counts.

This uses only eight pairs of shared-memory values for the reduction, rather than placing every thread’s running total in shared memory.

Add partial rows without atomic counters

A row may cross a batch boundary. Keep its partial left, centre and right counts on the GPU and add the next batch’s contribution. Only one block updates a given row in each batch, and batches are ordered, so these additions do not require atomic operations. The centre is tested only in the batch that contains it; the small primes omitted from the wheel contribute their separate counts once.
