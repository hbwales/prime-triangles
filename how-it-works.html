02

Generate base primes and allocate the batch buffers

make_base_primes(num_rows) → cudaMalloc → cudaMemcpyCPU setup, then one upload

The CPU sieves integers through \(N=\texttt{num\_rows}\), then builds sorted BasePrime records for primes from 19 through N. Each record contains p, a 32-bit reciprocal and a 64-bit reciprocal: 16 bytes on this build.

Why only primes through N?

Every composite \(x\le N^2\) has a prime factor \(p\le\sqrt{x}\le N\). Multiples start at \(p^2\): smaller composites already have a smaller prime factor, and p itself must remain set.

The temporary CPU sieve is destroyed when make_base_primes returns. The resulting base_primes vector stays alive because the CPU uses it to find each batch's active-prime count.

What each record stores

BasePrime {
    u32 prime;
    u32 reciprocal32; // floor(2^32 / p)
    u64 reciprocal64; // floor(2^64 / p)
}

For odd p, ~0ull / p gives the required 64-bit reciprocal: p cannot divide \(2^{64}\). Tiny inputs retain one harmless p = 19 record.

The host computes \(\texttt{last\_number}=N^2\) and rounds the wheel-byte length up to a multiple of four. It allocates gpu_sieve, uploads gpu_base_primes, and allocates gpu_prepared_primes. The latter two have one record per base prime. Runs through 8m rows use tile marking alone. Larger runs split at p = 2m and allocate gpu_sparse_state: one packed u32 per prime above that cutoff. sparse_begin marks the first of these records; the offsets are initialized lazily when primes first become active.

\[S=4\left\lceil\frac{\lfloor N^2/30\rfloor+1}{4}\right\rceil,\qquad |\texttt{gpu\_sieve}|=\min(S,256\,\mathrm{MiB}).\]

S is the total logical sieve length swept across the run. It is not allocated all at once.

03

Build and upload the repeating pre-sieve

make_presieve_pattern() → cudaMemcpy(gpu_pattern, …)CPU construction, GPU global-memory table

Before discussing the pattern, the representation matters: one byte stores the eight residues coprime to 30, in the order \(1,7,11,13,17,19,23,29\). A set bit means the represented number has not been eliminated.

\[x=30q+r\quad\longmapsto\quad\text{byte }q,\quad\text{bit }\operatorname{index}(r).\]

The modulo-30 byte

Green: represented and still set. Crossed out: represented but cleared. Plain cells have no bit. Display runs from bit 0 to bit 7, opposite the usual printed binary order. “Full sieve” is computed locally for this small illustration.

The CPU starts with all candidate bits set, then clears represented multiples of 7, 11, 13 and 17. This pattern repeats every \(P=7\cdot11\cdot13\cdot17=17017\) bytes, or 510,510 integer positions. 

words[i] = pattern[(4*i + 0) % P]
         | pattern[(4*i + 1) % P] << 8
         | pattern[(4*i + 2) % P] << 16
         | pattern[(4*i + 3) % P] << 24;

The returned array has P packed 32-bit words: 68,068 bytes. Since P is odd, stepping four bytes visits every alignment in the byte period. The helper's 17,017-byte working array disappears on return; the packed CPU array remains in run and is copied once to gpu_pattern.

Other device tables—bits[30], residues[8] and through[30]—are statically initialized read-only device arrays. Ordinary read-only loads allow different lanes to request different entries without the distinct-address serialization associated with constant-memory broadcasts.

05

Choose the next batch and its intersecting rows

for (first_byte …) → active primes → BatchParamsCPU loop; no new GPU allocation

Each iteration advances by 256 MiB of wheel bytes. B = first_byte is an absolute wheel-byte index; byte_count can be smaller in the last batch. Their represented integer interval is clipped to the requested endpoint:

\[\begin{aligned}\mathrm{lo}&=30B, &\mathrm{hi}&=\min(30(B+\text{byte count})-1,N^2),\\\text{first row}&=\begin{cases}1,&B=0\\\lfloor\sqrt{\mathrm{lo}-1}\rfloor+1,&B>0,\end{cases}\\\text{last complete row}&=\lfloor\sqrt{\mathrm{hi}}\rfloor, &\text{last intersecting row}&=\lceil\sqrt{\mathrm{hi}}\rceil.\end{aligned}\]

integer_sqrt corrects a floating-point estimate with integer divisions, so these row boundaries are exact. The CPU advances num_active_primes while \(p^2\le\mathrm{hi}\). Larger primes cannot yet have a required strike.

The host assembles BatchParams: first byte, byte count, active-prime count, first row, row count and pattern offset. It passes this small object by value to each kernel. This does not allocate another global array. The dummy prime keeps the tiny-input launch valid; its anchor cannot strike the batch.

Four event records delimit prepare → mark_batch → count. Marking includes the regular tile kernel and any required sparse-window kernels. All launches use the default stream, so each stage finishes before the next consumes its output.

Prepare each active prime for this batch

prepare_kernel<<<…, 256>>>(…)GPU: one thread per active prime

A preparation thread reads one BasePrime and writes one 16-byte PreparedPrime. Absolute positions need u64; the resulting anchor lets tile marking mostly use bounded 32-bit arithmetic.

\[t_0=\max\left(\left\lfloor\frac Bp\right\rfloor,\left\lfloor\frac p{30}\right\rfloor\right),\qquad\text{anchor}=pt_0-B.\]

Write a wheel-eligible multiplier as \(k=30t+r_j\). Then \(\lfloor pk/30\rfloor=pt+\lfloor pr_j/30\rfloor\). For each phase j, successive turns advance p bytes and keep the same output bit. 

u32 wheel = (turn == p/30 ? p % 30 : 0) << 24;
#pragma unroll
for (u32 phase = 0; phase < 8; ++phase) {
    u32 r = (p % 30) * residues[phase] % 30;
    wheel |= __popc(residue_mask & ((1u << r) - 1u)) << (phase*3);
}
High bitsMinimum first-turn multiplier residue
Low 24 bitsphase 7 · phase 6 · … · phase 1 · phase 0
eight 3-bit indices, not eight candidate flags

The population count maps the product residue to its bit index. The unrolled loop computes all eight mappings directly and packs their 3-bit indices into wheel. The high bits enforce \(k\ge p\) on the first turn, which enforces \(pk\ge p^2\) without striking p itself.

Why reciprocal division is exact

For word width w, the CPU stores \(R=\lfloor2^w/p\rfloor\). The high half of nR gives an estimate at most one below the exact quotient:

\[q_0=\operatorname{high}_w(nR),\qquad\left\lfloor\frac np\right\rfloor=q_0+\mathbf1_{\{n-q_0p\ge p\}}.\]

floor64 does this once per active prime per batch. locate uses floor32 within each tile. The one correction preserves exactness; no floating-point reciprocal is involved.

07

Mark regular primes, then apply persistent sparse strikes

mark_batch → mark_kernel → scatter_kernelGPU: shared tiles, then one thread per sparse prime

mark_batch passes the active-prime prefix through 2,000,000 to mark_kernel. Each block owns up to 98,304 wheel bytes, representing 2,949,120 integers. Runs through 8m rows instead pass all active primes to the tiled kernel. The block has 1,024 threads (32 warps). A full 256 MiB batch launches 2,731 blocks; the last owns only 64 KiB of valid data but requests the same 96 KiB shared allocation.

1 · InitializeRead repeating pattern into shared words.
2 · BarrierAll words initialized before any clear.
3 · MarkDense, medium and sparse prime paths.
4 · Barrier / exportWrite finished tile to global sieve.

Initialization and small-prime repair

Threads copy the packed pre-sieve directly to shared memory. For a full tile each thread initializes 24 words. In the first word of the entire run, (value | small_prime_bits) & ~1u restores 7, 11, 13 and 17, which the repeating pattern otherwise removes, and clears 1. The count-array seeds for 2, 3 and 5 remain separate.

Find a tile's first strike with locate()

For tile byte offset s, locate advances from the batch anchor by whole p-byte turns. It computes the minimum multiplier residue that can reach the tile, applies the square restriction when still in the first turn, then each phase starts at turn_byte + floor(p*r/30). If that phase is below the threshold, it advances one more p-byte turn.

Clear bits safely

A strike at tile byte offset at clears its bit inside word at >> 2. Different primes can strike the same word, even when they clear different bits. Shared-memory atomicAnd prevents one thread from undoing another's clear.

After a block barrier, threads write their words to disjoint positions in gpu_sieve. No global atomic is needed for this export. These bits have been sieved by the regular-prime prefix; when larger active primes exist, their clears follow in the next stage. The shared tile disappears when its block finishes.

Large runs: one thread walks each prime above 2m

After the shared-tile exports, mark_batch launches scatter_kernel for consecutive 16 MiB slices. Each thread owns a prime and walks its hits in increasing multiplier order. Global atomicAnd combines clears from different primes. There is no shared tile or subgroup synchronization in this kernel.

1 · RestoreLoad the next byte offset and multiplier phase.
2 · Walk hitsAdvance each hit; clear only if it passes the divisibility filter.
3 · CarrySubtract the window length and pack one u32.
4 · Next windowDefault-stream ordering makes this state available.

Let \(R=(1,7,11,13,17,19,23,29)\), and let s be the current multiplier phase. Its byte offset within one p-byte wheel turn is \(d_s=\lfloor pR_s/30\rfloor\). To advance a hit at byte a:

\[s'=(s+1)\bmod8,\qquad a'=a+d_{s'}-d_s+p\,[s=7].\]

The bracket is 1 on phase wrap and 0 otherwise. The actual bit is selected by the prepared product-residue mapping in wheel; multiplier phase and output bit are different concepts. The phase step visits only represented multiples of p, in order, without reconstructing eight independent phase origins in each window.

Skip clears already covered by the pre-sieve

The loop still visits every wheel hit. Before issuing its global atomic, it tests whether the target is divisible by 7, 11, 13 or 17. Those bits were already cleared when the shared tile was initialized, so the atomic can be omitted. This uses integer arithmetic rather than another sieve or pattern-table load.

Let b be the absolute byte index of the window, a the hit's byte offset, and \(P=7\cdot11\cdot13\cdot17=17017\). The kernel receives \(u=b\bmod P\) and computes

\[z=30(u+a)+(pR_s\bmod30).\]

The actual represented integer is \(x=30(b+a)+(pR_s\bmod30)\). Their difference is a multiple of 30P, so z and x have the same divisibility by every pre-sieve prime. The clear is issued only if all four remainders are nonzero. A compile-time bound ensures z fits in u32 for a full window.

\[\rho=\frac67\frac{10}{11}\frac{12}{13}\frac{16}{17}\approx0.677.\]

About 67.7% of the candidate global clears remain; approximately 32.3% are avoided. The loop and phase progression remain unchanged. This lower atomic cost makes a 2m tiled cutoff worthwhile for large runs. Runs through 8m rows retain the original all-prime tiled path.

When a reaches or passes window length W, the next window starts with offset a − W and the same phase. Both values fit in one u32:

3 bitsphase s
29 bitsnext byte offset a − W
\[\text{state}=((a-W)\mathbin{\vert}(s\ll29)),\qquad a=\text{state}\mathbin{\&}(2^{29}-1),\quad s=\text{state}\gg29.\]

A compile-time bound checks that a batch plus one prime step fits in the offset field. Newly active primes use locate(record, window_offset, …) in every window of their first batch, enforcing the square restriction even if their first hit is in a later window. From the following batch onward, their packed carry is reused. One thread owns all reads and writes for a prime, so the state needs no atomics.

At 50m this state occupies 10.88 MiB, down from 75.11 MiB in the previous eight-offset layout, despite the lower cutoff including more primes. The sparse path still visits every active large prime once per window. It avoids visiting each one in every 96 KiB tile and builds no bucket queues.

Why the original all-prime tile path scales poorly

In the original baseline, the general prime loop visits every active record in every tile, including records that produce no strike. Summing the actual batch/tile bounds and prime counts gives about 2.018 × 10¹² visits at 5m rows and 1.732 × 10¹⁵ at 50m: 858× more visits. These are logical record visits, not measured DRAM transactions; caches and prefetching can serve repeated loads.

With fixed tile size, this component tends toward \(O(N^3/\log N)\) as active-prime lists grow. Sieve positions and word scans grow as \(N^2\). These competing costs explain why a simple 100× extrapolation from 5m to 50m is unsafe.

Count each row inside the completed GPU batch

count_kernel<<<batch.row_count, 256>>>(…)GPU: one block per intersecting row

The count kernel runs only after regular marking and every sparse window complete. Its 256-thread block computes row endpoints a, m and b, then calls count_range for the left interval [a, m − 1] and right interval [m + 1, b]. Each interval is clipped to this batch.

Four wheel bytes form one 32-bit word covering 120 integers. Thread t reads words first_word + t, first_word + t + 256, … . Interior words contribute __popc(word); endpoint masks exclude represented values outside the interval.

Example: count primes in [37, 49]

Byte q = 1 represents 31, 37, 41, 43, 47, 49, 53, 59. Range bits select 37…49; the sieve has already cleared 49 = 7². 

sieved byte: 11011111
range mask:  00111110
AND:         00011110 → popcount = 4

Binary strings show bit 7 first. The four survivors are 37, 41, 43 and 47.

Warp reductions combine each side's thread-local totals. Eight uint2 warp totals use just 64 bytes of shared memory. After a barrier, the first warp reduces those pairs. Thread zero tests the centre bit separately and adds all three contributions to gpu_counts[row].

One block updates a row in this batch. Later batches add to that row in stream order, so these per-row additions need no atomics. A row's three u32 fields fit the supported row limit; cumulative CSV totals on the CPU use u64.

Race::emit → write_csv_row → progress checkCPU only, after each completed batch

rows_written advances through the newly completed rows. Race::emit adds each RowCounts to the u64 cumulative left, centre and right totals, updates leader statistics, and writes one CSV record.

\[L_n=\sum_{j=1}^n\ell_j,\quad C_n=\sum_{j=1}^nc_j,\quad R_n=\sum_{j=1}^nr_j,\qquad L_n+C_n+R_n=\pi(n^2).\]

The CSV writer uses std::to_chars for four integers, adds commas and a newline, and passes the resulting byte span to write_output. Four maximum-width u64 values plus delimiters fit exactly in 84 bytes. No per-row formatted string is allocated.

11

Flush, report and exit

flush_output → final diagnostics → returnAfter the loop

When all batches finish—or Ctrl+C requests a stop—the program flushes stdout, reports the final timings and counts, then returns. An interrupt sets a lock-free atomic flag; it does not interrupt a running kernel or emit an incomplete row. The signal handler re-registers itself to accept repeated Ctrl+C requests.

CPU vectors and arrays are destroyed when run returns. The current one-shot program relies on process exit to reclaim GPU allocations and events. Calling run repeatedly inside a long-lived process would require explicit cleanup or resource-owning wrappers.

CUDA, parsing and output failures throw exceptions. The catch in main writes # Error: … and returns 1. Normal completion and a graceful Ctrl+C stop return 0.

This walkthrough follows the current tri.cu. Static memory estimates and the 50m work counts were calculated from its bounds; no full 50-million-row run was performed. The only external dependency of this document is KaTeX and its fonts from the CDN.

Scaling with the row count

N rows cover \(X=N^2\) integers. Let B = 256 MiB be the batch size, t = 96 KiB the shared-tile size, and W = 16 MiB the sparse-window size, all measured in wheel bytes. A wheel byte covers 30 consecutive integers.

\[\text{batches}\simeq\frac{N^2}{30B},\qquad \text{tiles}\simeq\frac{N^2}{30t},\qquad \text{windows}\simeq\frac{N^2}{30W}.\]

There are 310,441 batches at 50m rows. A constant cost per batch would produce quadratic scaling. Actual batch cost grows as more primes become active.

Count the work, before fitting the time

Define \(\Pi(u)=\#\{p:19\le p\le u\}\), \(S_j(u)=\sum_{19\le p\le u}p^j\), and \(H(u)=\sum_{19\le p\le u}1/p\), with each sum over primes. Let C = 2m for a large run; for a run through 8m, C = N. A prime p is active over approximately \(N^2-p^2\) integer positions. Summing those lengths gives the visit counts:

OperationApproximate countLarge-N growth
Tile prime-record visits\(V_t=\dfrac{N^2\Pi(C)-S_2(C)}{30t}\)\(\Theta(N^2)\), fixed C
Sparse prime/window visits\(V_s=\dfrac{N^2[\Pi(N)-\Pi(C)]-[S_2(N)-S_2(C)]}{30W}\)\(\Theta(N^3/(W\log N))\)
Preparation visits\(V_p=\dfrac{N^2\Pi(N)-S_2(N)}{30B}\)\(\Theta(N^3/(B\log N))\)

These visit formulas ignore batch/window boundary rounding and the early activation of a prime within its first batch. They describe logical visits, not DRAM transactions. From \(\pi(N)\sim N/\log N\) and \(S_2(N)\sim N^3/(3\log N)\), the leading sparse-visit term is \(N^3/(45W\log N)\); preparation has the same form with B replacing W.

Composite-strike counts are different from visit counts. If

\[F(y)=8\left\lfloor\frac y{30}\right\rfloor+\#\{r\in R:r\le y\bmod30\},\]

then the exact number of wheel-loop hits up to \(N^2\) is

\[M(N)=\sum_{19\le p\le N}\left[F\!\left(\left\lfloor N^2/p\right\rfloor\right)-F(p-1)\right].\]

This counts represented multiples \(pk\) with \(k\ge p\). It grows as \(\Theta(N^2\log\log N)\). To count the filtered global atomics exactly, define \(F_P(y)=\sum_{d\mid P}\mu(d)F(\lfloor y/d\rfloor)\), where the square-free divisor's sign \(\mu(d)\) alternates with the number of factors. Replace F by \(F_P\) and sum only over p > C. At 50m, the sparse loop visits about 114.23 trillion hits and issues about 77.33 trillion atomics after filtering. It does not eliminate the loop iterations.

Asymptotic growth versus the useful operating range

\[\text{work}=\Theta\!\left(N^2\log\log N+\frac{N^3}{W\log N}+\frac{N^3}{B\log N}\right),\quad C\text{ fixed}.\]

This is an operation-count model with fixed hardware, ignoring the implementation's finite row cap. Since B and W are fixed, the prime-visit terms eventually dominate. The code is therefore not asymptotically just a textbook \(N^2\log\log N\) sieve. For small runs that tile every active prime, the tile-visit term instead has \(\Theta(N^3/(t\log N))\) growth.

There is little empty sparse-window work at 50m. Consecutive modulo-30 multiplier residues have maximum gap 6, so a prime's byte gap is at most \(\lceil p/5\rceil\). When \(N\le5W\approx83.9\text{m}\), every active prime has a modulo-30 candidate hit in every full window, apart from activation and clipped edges. Bucket scheduling could improve the eventual visit bound, but in this range it would mostly schedule work that already has a hit, while adding queue traffic.

The calibrated runtime model has an effective exponent of about 2.25 over 10–50m. That describes this configuration and range; it is not a new complexity bound. Space grows as \(O(N+\pi(N)+B)\): the GPU's full row-count array is linear in N, prime records and carry are linear in \(\pi(N)\), and the sieve batch is fixed-size.

Measured rate model and cumulative runtime

For a full late-range batch, the fitted combined preparation, marking and counting time is

\[r(n)\approx10.580+1.136\frac{\pi(n)-\pi(C)}{10^6}+35.482[H(n)-H(C)]\quad\text{milliseconds},\quad C=2\text{m}.\]

The fixed term covers the capped tiled prefix and fixed per-batch work. Prime-count and reciprocal-sum features track window visits and strike density. Their fitted coefficients are empirical and correlated; they are not independently measured instruction costs. Eleven configurations from 8.1m through the row cap gave 3.3% RMS fit error. Leave-one-out prediction had 5.1% RMS error and a 9.4% maximum error.

A full 10m run took 189.7 seconds and matched all 405,147,067 CSV bytes against the existing 35m prefix. Its final progress intervals were about 1.219 times slower than the short-sample rate fit. The cumulative model applies that factor and integrates batch cost against the number of integer positions:

\[T(N)\approx189.7+\frac{1.219}{30B\cdot1000}\int_{(10^7)^2}^{N^2}r(\sqrt{x})\,dx\quad\text{seconds},\qquad N\ge10^7.\]

The factor 1000 converts milliseconds to seconds. The integral has a direct prime-sum form: \(\int\pi(\sqrt x)dx=x\pi(\sqrt x)-\sum_{p\le\sqrt x}p^2\), and \(\int H(\sqrt x)dx=xH(\sqrt x)-\sum_{p\le\sqrt x}p\). The exported data records the coefficients, prime sums, work counts, samples and sustained correction.
